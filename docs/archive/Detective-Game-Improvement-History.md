**第一轮：让当前案件行为一致**

01. 统一调查数据的解释规则。

当前 `CreateSpeciesMarker` 对核心物种优先采用案件资产，`BuildSpeciesTooltipDetails` 却直接采用外部 survey record。外部传入当前鲨鱼已检测时，提示可以显示 Detected，地图和记事本仍显示案件中的未检出。历史记录的非检测状态也需要检查：目前外部非检测的地图样式受 `!historical` 限制。

建议先明确采用“固定教学案件”：核心线索及结论由案件定义控制。导入层检查 case、调查批次、站点、时期与数据有效性，对无法与当前案件兼容的输入给出明确原因和返回路径；单独提供用户主动选择的独立案件入口。可兼容的额外物种作为调查背景展示，其是否可用于破案应有明确标记。不同站点或不同时间的检测与非检测不能直接当成冲突，需要先确定聚合规则。

实现一个统一的调查展示摘要，供地图、tooltip 和 Notebook 使用；证据判定只读取经过明确映射的案件证据。保留原始输入的来源、质量和置信度。旧 `detectedSpeciesIds` 与新 `speciesObservations` 同时存在时，需要定义去重及详细记录优先规则。整理 Unknown、多条同物种记录、时期不明确及缺少可选字段的处理方式。

主要位置：`InvestigationCaseRosterBuilder`、`InvestigationStateUpdater.TryApplyExternalInput`、`InvestigationState.FindSurveySpeciesRecord`、`InvestigationRuntimeView.Observe`。

验收：同一条调查记录在各处的时期、检测状态及来源一致；不兼容输入不能悄悄改变案件事实；额外物种不会阻断五个核心观察；无外部输入时仍可完整通关。用包含冲突输入、详细/旧格式混用、历史非检测、Unknown 和不同站点记录的固定样例验证。

02. 将观察门槛收归 Domain。

目前界面 `CountInitialFindings` 排除 Methodology，只计算 Observe 阶段的证据；`TrySetPhase` 和 `TryRunThreat` 使用全部 `DiscoveredObservationIds.Count`。四条物种观察加一条方法学说明即可凑成五条。

建议由 Domain 根据当前案件的核心观察集合计算 readiness，界面进度、Edna、阶段切换和运行模型共用结果。使用明确的必要证据集合，避免以后添加背景说明时再次影响门槛。

验收：四条核心观察加任意说明都不能解锁；五条完整核心观察可以解锁；重复点击不增加进度；从顶部阶段按钮和 Controller/API 进入时行为一致。

**第二轮：让玩家更容易观察、比较和修订**

03. 改进 Observe 的调查反馈。

地图上的物种增加轻量的“已记录”标记，采用形状或图标，并在物种详情中显示文字状态。已记录的物种仍可查看。查看同一物种时，让历史图与当前图中的对应标记同步强调，帮助玩家在散布布局中建立联系；如果某时期没有记录，明确写“没有提供该时期记录”。

统一 hover、键盘聚焦和点击后的详情，展示时期、调查结果、来源及记录状态。修订 Edna 中“还要找几个变化”的表述：当前五条必收证据也包括稳定物种，应引导玩家同时记录变化与稳定的对照。导入的背景物种注明“补充调查资料”，避免让玩家误以为点击它能完成核心目标。

验收：玩家能辨认哪些物种已记录；同种在两图之间可追踪；不会因为重复点击或背景物种而误解进度。鼠标、键盘和触摸均可完成。

04. 增加轻量的假说对照摘要。

保留现有“选原因 → 运行 → 选预测 → 选证据 → 判断”的逐步操作，在 Notebook 或可展开区域增加四种假说的摘要。每种假说显示玩家已经完成的“支持、挑战、待查”记录，点击可回到对应比较。

摘要从已有 `ComparisonRecords` 派生，避免维护第二套评分状态。尚未运行、未发现或 ROV 后才解锁的信息保持隐藏；证据不足作为待查，不计成支持或挑战。记录数量只代表比较历史，不换算为胜率，也不用于自动推荐正确答案。

主要位置：`SimulationModels`、`InvestigationState`、`InvestigationRuntimeView.Simulate`、`InvestigationRuntimeView.Notebook`。

验收：摘要与已保存比较逐条对应；切换原因不丢选择与阅读位置；长线捕捞和底拖网的共享模式仍需要底栖证据加以鉴别；摘要不会提前泄露后续线索。

05. 改进判断与报告反馈。

比较后的反馈保持在当前“预测—证据”附近，明确关联到所选的两项内容。按不相关证据、相反变化、证据强度不足等类型给出解释，保留玩家修订入口。

提交初步解释之前，清楚展示即将提交的假说名称和当前已完成比较，让玩家能够确认或切换假说。当前提交动作使用选中的模型 ID，需要确保“刚查看过哪个模型”和“准备支持哪个解释”在交互上清楚可辨。

最终报告保留四个现有问题。检查报告时，在缺失或不符合要求的具体区块标记原因，并将滚动和焦点定位到第一处需要处理的位置。延续已有证据分类进度；结案摘要可引用玩家自己选取的线索，帮助回顾判断过程。

验收：玩家知道哪个区块需要修改，其他选择保持不变；提示不会代选证据或填写推理；错误提交与材料不完整仍按现有规则分别处理。

06. 调整 Edna 引导与阅读负担。

现有引导已有三级提示和错误升级。下一步检查提示的重置粒度：目前 `activeGuidanceStep` 使用通用步骤枚举，切换到另一个假说的相同步骤时，可能保留过细的提示级别。建议任务标识包含阶段、假说、预测或目标，既能在新任务重置，也能在同一问题上保留帮助。

Easy 在完成一次“选预测—选证据—判断”后，可试验减少自动高亮，仍让玩家主动请求 More help。Hard 保留所有必要的状态、操作反馈和错误解释。降低引导只影响提示强度，不改变证据和科学规则。

对主要按钮和阅读区域做实际视口验证。源码中部分导航高度为 28 个 Canvas 单位、标签字号为 11，不能只据这些数值判断物理大小；需要测量 Canvas 缩放后的点击区域与阅读效果。先验证桌面 1280×720、浏览器嵌入 960×600，再检查产品确认需要支持的触摸竖屏。允许布局增高、换行和滚动，避免靠持续缩小文字容纳内容。

验收：关键文字、按钮和反馈无遮挡；纯键盘可完成全程；打开 Notebook 后焦点和返回位置合理；减少动态效果模式下仍能理解因果变化；新目标的帮助级别按约定重置。

07. 用一次小规模试测决定后续投入。

找约五位符合目标年龄与使用场景、未见过本案的人，先让他们独立游玩，再访谈。目标年龄、实际使用设备和预期单局时长仍待产品确定；本计划暂以现有浏览器演示场景为主，不假设已验证的儿童阅读水平。

记录：找到第一个观察用了多久、在哪里重复点击、何时请求提示、哪个阶段停滞、是否理解稳定物种的作用，以及是否能解释两种捕捞假说为何难以区分。结束后让玩家用自己的话解释一项支持结论的证据和一个仍存在的限制。

建议的第一轮试测目标是至少四人无需开发者口头指路完成主流程，并能说明底栖线索在鉴别中的作用；这是迭代目标，不是当前成果或统计结论。采用观察笔记或本地 QA 记录即可。根据卡点修改下一轮范围。

**第三轮：连续体验、接入与维护**

08. 保存并继续调查。

目前调查状态和桥接结果在内存中，只有减少动态效果偏好已有持久化。建议保存 case ID、案件/存档版本、输入摘要、已发现证据、已完成比较、报告草稿及难度。通过可验证的快照恢复规则状态，并在加载时检查数据与案件版本是否兼容。

验收：在 Observe、Simulate、ROV 后和 Report 各退出一次均能继续；清空或不兼容存档有明确恢复路径；重开案件与继续调查含义清楚；在实际 WebGL 运行环境验证刷新及重新打开后的行为。

09. 准备真实接入与构建入口。

先为 `InvestigationGameInput` 写好固定样例，覆盖有效输入、错误案件、缺少字段、额外物种及矛盾数据，再与前序小游戏共同确定传入时机。定义输入何时消费、何时清除、Restart 是否重用，以及主流程如何消费完成结果，避免静态 `PendingInput` 或 `LastResult` 残留到下一次调查。

为当前独立演示提供明确的 Investigation 启动构建；团队完整流程确定后再统一入口。默认 Build Settings 仍以 SampleScene 开头，专用构建工具则直接指定 InvestigationScene，两条路径需要明确区分并各自验证。

验收：从前一小游戏进入时能看到一致的调查上下文；结案后主流程收到一次有效结果；重新开始没有旧结果残留；真实 WebGL 构建可完成完整流程。

10. 渐进拆分界面并测量刷新成本。

`InvestigationRuntimeView` 的六个 partial 文件累计约 4,900 行，`RenderAll` 清空并重建内容、停止协程并强制布局。建议先测量选证据、切换模型、打开 Notebook 和视口变化时的帧耗时、分配与布局开销，再决定优化范围。

随着第二轮界面改动，逐步抽出物种标记、证据卡、比较工作区、Notebook、报告表单和引导条；保留 Domain 的规则职责。优先让选择态和提示文字局部更新。动画协程分开管理，检查全局停止协程是否会遗留待刷新标志或打断交互。

验收：行为与已有流程一致；焦点、滚动和动画中途操作有回归验证；有同一设备、同一操作路径的前后测量。现阶段只确认重建方式，尚未证明它造成实际卡顿。

**可选更新：单独试验后决定是否进入主线**

| 更新方向 | 最小可试验版本 | 决策依据与依赖 |
|---|---|---|
| 运行前做一次预测 | 每案选一个模型，让玩家先猜一个物种变化，运行后对照解释；可跳过且不改通关评分 | 观察是否增加推理，还是只增加点击 |
| 亲自组织因果链 | 在结案复盘提供“选择节点 → 选择关系”的短互动，支持键盘/触摸；先保持报告原判定 | 现有食物网和推理选项可复用，关系含义需内容审核 |
| 主动选择补证问题 | ROV 前让玩家说出“还想验证什么”，再展示当前固定两条证据 | 先提供反思机会；分支采样要另行设计全部证据与目标依赖 |
| 结案后的迁移题 | 一道改变某条证据条件的可选题，反馈解释推理变化 | 每个条件单独编写并审核，保持主案件事实稳定 |
| 物种图鉴与表现 | 先给实际展示的额外物种补齐一致风格的图像和简短介绍；复用当前 tooltip/Notebook | 核实素材授权和物种识别，优先有玩家接触的内容 |
| 轻量音效 | 发现、提交比较、ROV 到达各一类提示；提供静音，视觉反馈仍完整 | 在浏览器中验证播放与静音行为 |
| 第二个案件 | 第一案试测稳定后，为不同原因设计完整观察、模型、目标、ROV、报告和复盘 | 当前 validator 固定五物种、四威胁、20 目录等约束，且部分文案/证据 ID 写死，需要先梳理可配置边界 |

**建议拆成的实施批次**

第一批交付 01–02：数据一致性和门槛修复，附输入边界测试。之后才接真实上游数据。

第二批交付 03、05 和 06 的必要部分：观察标记、稳定物种文案、局部反馈、初步解释确认、报告定位与提示重置。它们改动较集中，玩家收益直接。

第三批交付 04 并执行 07：加入假说摘要，让玩家试测决定是否需要新的预测或因果链互动。

第四批根据使用场景选择 08–10：课堂或长会话优先保存；团队演示优先接入与构建；实际性能问题优先局部刷新。组件拆分可以随每批改动逐步完成。

验证时保留现有 58 项测试作为已知基线，更新确实随界面规格变化的断言。新增测试重点覆盖输入语义、阶段边界、摘要不泄露线索、报告恢复和存档重放；每批执行受影响测试，在形成可演示版本时跑完整流程。仅修改此计划无需重新运行游戏测试。

本计划中的错误定位与恢复建议参考了本地 UI/UX 技能的对应指南；渐进呈现检索未得到相关匹配，因此相应建议依据当前项目已有交互及代码分析。未来增加生态关系或改变科学解释，需要结合项目内容审核再决定。
